1024程序员节

今天跟着“1024程序员节”的课表开始学 Python。上午的进度虽然只推进了两节（复习基础语法 + 函数）为了防止自己“学了就忘”，我把上午的踩坑记录和知识理解整理了一下。

一、 被 while 和 break 折磨

今天写的第一个完整程序是“重启终端：口令 1024 。代码虽然不长，但我调了好几次。

给自己记下的两个教训：

  1. check_count = 0 必须写在 while 外面！ 我今天才彻底搞懂，如果把这个记分牌写在 while 里面，每次循环一开始，分数就被强行清零了，永远也攒不够 3 次 。
  2. 不加 break 就是是个死循环。 while True 是个无底洞，如果我不写 break 去结束它，即使输入了 exit ，程序也会继续问我 请输入学习内容 。

二、 懂了，但没完全懂的函数（参数和返回值）

上午重点学了 def 定义函数。我把函数整合到了打卡器里，写了进阶版的代码：

我们总说“定义一个函数”，我查了一下其实代码里的 def 就是英文 define（定义）的缩写。
那函数又是什么：你放进去 参数 ，按下启动键 执行代码，最后出来了 返回值 。它最大的好处就是把一堆干活的代码“ 打包 ”起来，起个名字，以后需要用到的时候，喊一声名字就行了，不用重复写。

  • def ：给电脑下达“造机器”的指令。
  • calculate_exp ：给这个机器起的名字（以后叫名字就能用它）。
  • ( times )：机器接收参数的地方，得往里面塞个东西，机器才能运转。
  • :（冒号）：这个很重要，它相当于宣告：“ 机器内部的构造说明书，从下一行开始！”所以下一行必须要缩进。
    我理解的 ：原来 def 只是在“画图纸”和“造机器”。只要电脑没看到你 “ 按开关 ”（也就是没看到你调用 calculate_exp(3)），这台机器造好了也只会静静躺在那里，根本不会自己跑起来。只有调用它，它才会开始工作。

脑补：print 和 return 到底差在哪？
这是上午最卡我的地方。我还以为写个函数让它打印出来就完事了，今天才明白：

  • return 是交还结果：函数算完账，用 return 把数据悄悄塞回给外面的变量（ my_exp ），这一步在屏幕上是看不见的。
  • print 只是让你看个响：外面拿到了 my_exp 这个数据后，我再写个 print，屏幕上才会出现“获得经验值”。

    总结 ：没 return，外面的程序就接不到数据；没 print，我就看不到结果。

三、 实战做题：

上午做了一道限时题：算算距离 1024 经验差多少，如果超额了就输出 0，且要求不要打印任何提示语。
我提交的正确代码（后面还有翻车操作）：

第一步：接收输入

题目要求 “ 输入一个非负整数 ” ，然后题目是说：“不要打印任何提示语”。

所以，代码不能写 input(“请输入…：”)，只能写：n = int(input())

第二步：算差值

题目说“每完成一道题获得 32 点经验”，那目前的经验就是 n * 32。目标是要攒够 1024 点经验，那距离目标还差多少呢？

就是拿总分减去当前分：1024 - (n * 32)。我把这个算出来的差值装进一个变量里，叫它 diff：

diff = 1024 - n * 32

复盘时的反思：现在我觉得叫 task_count 更好
我上面交上去的代码里，变量用的是 n。这是数学题的老习惯，我当时图省事就写了。
但现在写这篇复盘博客时，我越看越觉得不对劲。代码不仅是给电脑跑的，更是给人看的。n 过几天我自己可能就忘了是啥意思。
如果把它起名叫 task_count（ 任务数量，也可以理解成题目数量 ），一眼就能看出这是“ 完成的题目数量 ”，可读性强多了。

第三步：判断输出
题目要求：如果还没达到，输出差值；如果达到或超过了，输出 0。
这时候就要看 diff 的值了：

· 如果 diff > 0：说明还没到 1024，那就直接输出差值。
· 如果 diff <= 0（也就是 else）：说明不仅到了，还可能超额了（差值是负数或者0），题目要求这种情况输出 0，那就直接 print(0)。
总结一下我的思考：
刚开始做题时，我容易在“大于、小于”里面绕进去（这也是我踩坑第 3 点写的，看别人写成 if diff >= 1024 直接绕晕了）。
后来我想明白了：我只要关心“还差多少（正数）”就行了，至于超过的部分，题目说不用管，直接给个 0 就行。

运行时我的翻车操作：

1. 输入空回车会死机 ：我运行测试的时候手欠，直接按了回车，结果报错，具体它写的什么不记得，但是大概意思就是：int( ) 遇到空字符串（空气）直接罢工了。以后测试这种题，千万不能习惯性按回车。

2. 不要乱加提示语：平时习惯写 input(“请输入…”)，但是系统它只认纯数字。

3. 逻辑差点写反：差值是 1024 - 得分。如果超额完成，这个差值就是负数。所以判断是否输出 0，条件是 if diff <= 0 或者像上面那样 if diff > 0 走正常流程。看别人代码时，发现有人写成了 if diff >= 1024，逻辑直接就绕进去了。

1. 文件路径 ：

课上的笔记写了这两个概念，我一开始也绕晕了，后来用快递地址和指路来理解，瞬间就通了：

绝对路径 ：( 像写快递地址 )

  • 概念：从电脑的“盘符”（比如 C盘、D盘）开始，一直写到你想要的文件名，一步都不落下。
  • 代码示例：C:\Users\1\Desktop\today\test\test2.txt

    我的理解：就像寄快递，必须写明“中国-江西省-南昌市-某某区-某某路-某某小区-几栋几号”。不管你人在哪里，只要拿到这个完整的地址，就一定能找到目标。

相对路径: ( 像在家里指路 )

概念：以你当前运行的代码文件所在的位置为起点，去找到目标文件。

代码示例 ：

  • 如果文件和代码在同一个文件夹里，直接写文件名就行：“test2.txt” 。
  • 如果在代码文件的上一级目录，写：“…/test2.txt” 。

    我的理解：就像你在家里坐在沙发上，跟室友说 “ 去厨房拿个苹果 ”。你不需要说 “ 去地球上中国某某小区的厨房 ”，因为室友（电脑）知道你现在就在家里（当前代码目录），它顺着你的位置去找厨房就行。

  • 注意 ：Windows 路径里有反斜杠 \，为了防止被识别为转义字符（比如 \n），前面一定要加个 r（代表 raw string）。

2. 编码 (encoding)：

  • 一定要写 encoding=“utf-8” 。如果电脑默认用 GBK ，读中文就会乱码。
  • 为什么一定要写？ 记得课上学长说的：计算机底层只认识 0 和 1，把中文变成 0 和 1 的规则就叫 “ 编码 ”。不同系统默认的编码不一样（这是我查的Windows 经常默认是 GBK，而 Mac/Linux 默认是 UTF-8）。
  • 乱码：如果不指定 encoding=“utf-8”，写进去的中文在别人的电脑上打开可能全是一堆问号或者“锟斤拷”。
  • 结论：只要写文件，无脑加上 encoding=“utf-8”

3. 模式 (mode)：

这是最核心的参数，决定了你打开文件后能干嘛：

  • mode=“r”（只读模式，默认）： 只能看，不能改。如果文件不存在，程序会直接报错 FileNotFoundError。

课后补充：带 + 和 b 的模式：

  • r+、w+、a+ ：代表既能读又能写。
  • rb、wb ：代表以二进制模式读写。如果要处理图片、视频、音频这些非文本文件，就必须用带 b 的模式，且不能指定 encoding 。

总结：
平时写代码，如果能用相对路径（比如就直接写 “log.txt”）就用相对路径，因为代码挪到别的电脑上也能直接跑。

如果实在找不到，或者必须用绝对路径，记得在 Windows 下加个 r 防转义

基础异常处理：

有了文件操作还不够，如果用户乱输入，程序还是会崩溃。我写了个“成绩查询系统”来练习 try 和 except 。

结合我的成绩查询代码，它的运行逻辑是这样的：

1. try（尝试区）：

我告诉电脑：“ 你先试着执行这两行代码 ”。如果我输入了“ 数学 ”，字典 scores 里面有，电脑顺利打印出成绩。
2. except KeyError（兜底区）：

如果我手欠，输入了“ 物理 ”或者“ 体育 ”或者其他什么，字典里根本没有这个键。按照以前的脾气，电脑会直接爆红报错（KeyError），程序当场死机。
但现在我写了 except KeyError: 这就相当于告诉电脑：“如果你遇到了找不到键（KeyError）的错误，别死机，来执行我这里的代码。”所以它会温柔地打印一句：“ 没有找到该科目的记录 ”。
3. else（顺利区）：

只要 try 里面的代码没有发生任何报错，顺利跑完了，它才会接着执行 else 里面的代码。
我的脑补 ：
以前只要我输入错东西，程序直接一片爆红死机。现在有了 try 和 except：

  • try 就是 “ 你试着跑一下 ”。
  • except KeyError 就是 “ 如果报了这个错，我来接住 ”。
  • else 是 “ 如果一切顺利，最后打印这句话 ” 。

    这样程序就有了容错能力
